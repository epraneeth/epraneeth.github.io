What I want to measure in a tool-using agent

This is a protocol for future experiments. No benchmark results are reported here. Drafted with AI assistance.

A successful demonstration tells me that an agent can complete a task once. I want to know whether it completes the task reliably, what happens when a tool fails, and how much the successful outcome costs.

Start with an observable outcome

My starting point is a small, versioned set of retrieval and tool-use tasks. Each task should specify the input, available tools, initial state, and an independently checkable success condition.

For a grounded answer, I would check the cited evidence as well as the answer. For a state-changing workflow in a sandbox, I would inspect the final state. A statement that an action succeeded is not enough to establish that it happened.

Compare small changes

I plan to compare a simple agent loop with controlled changes: clearer tool descriptions, bounded retries, and explicit state checks. The model, task set, resource budget, and measurement conditions should stay fixed within each comparison.

Failure cases should include unavailable tools, malformed responses, missing evidence, and attempts to redirect the agent through retrieved content. Each failure needs a label and a trace, so an aggregate score does not hide the underlying behaviour.

Keep the measurement honest

  • Completion: verified task outcomes, including abstention when the task cannot be completed correctly.
  • Recovery: outcomes on tasks with injected failures, reported separately from normal tasks.
  • Resources: latency, tool calls, token use, and cost per attempted and successful task.
  • Variation: repeated trials and uncertainty estimates, with failures included in the denominator.
  • Grounding: citation presence and evidence matching, followed by a separate check that the evidence actually supports the claim.

I would separate development tasks from a held-out evaluation set. If a case has ambiguous success criteria, I would repair the task specification before treating its score as a signal about the agent.

What I want to publish

A useful result should come with the exact configuration, task-set version, run commands, raw trial records, and a short account of the failures. A negative result is useful too: if an extra retry increases cost without improving completion, that is worth reporting.

This design draws on Anthropic’s guide to agent evaluations, particularly its distinction between transcripts and outcomes and its discussion of deterministic, model-based, and human grading.
